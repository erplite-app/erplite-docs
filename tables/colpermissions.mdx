Column permissions control access to individual fields inside a table. Use them when users need access to the table but should not see or change every field.

## When Column Permissions Help

Use column permissions for:

- Pricing, margins, or financial fields.
- Internal notes not visible to vendors or restricted users.
- Approval fields only managers should edit.
- System-managed fields users should not change.
- Personally identifiable information.
- Sensitive customer or supplier details.

## View vs Edit

| Permission | Behavior |
|------------|----------|
| **Can view** | User can see the field value. |
| **Can edit** | User can change the field value where editing is allowed. |

A user who cannot view a field should not rely on it for day-to-day decisions because it will be hidden or unavailable in their experience.

## AI Guidance

### When to Use This Feature

An AI should use column permissions when table-wide access is correct but a subset of fields is sensitive or should be controlled by managers, finance, or automations.

Do not create a duplicate table just to hide a few fields. Use column permissions first.

### How to Use It

<Steps>
  <Step title="Identify sensitive fields">
    Mark fields that should not be visible or editable to every table user.
  </Step>
  <Step title="Open column settings">
    Edit the column and open its permissions section.
  </Step>
  <Step title="Choose viewers and editors">
    Select the users, teams, or roles that can view and edit the field.
  </Step>
  <Step title="Save the column">
    Save the table changes.
  </Step>
  <Step title="Test with different users">
    Confirm the field appears and edits only for the intended people.
  </Step>
</Steps>

### How to Verify

The AI should verify:

- A permitted user can see the field.
- A permitted editor can update the field.
- A restricted user cannot see or edit the field.
- Views, imports, exports, reports, and relation displays do not unintentionally expose restricted values.
- Automations that depend on the field still work as intended.

## Best Practices

- Use roles or teams for column permissions instead of individual users where possible.
- Use derived fields for read-only calculated values instead of editable sensitive formulas.
- Re-check column permissions after importing new fields or copying tables.
