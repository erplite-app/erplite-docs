Table permissions define the actions a user, team, or role can perform on a specific table.

## Permission Groups

| Group | Permissions |
|-------|-------------|
| **Table** | View table, duplicate table, delete table, rename table, manage columns, manage views. |
| **Records** | View records, create records, edit records, delete records, manage layout, comment. |
| **Misc** | Manage table automations, manage sharing. |

## Recommended Permission Sets

| Set | Typical Permissions |
|-----|---------------------|
| **Owner/Admin** | Full access, including sharing, columns, views, automations, and records. |
| **Manager** | View, create, edit, comment, manage views, and use workflow actions. |
| **Operator** | View, create, edit assigned records, and comment. |
| **Viewer** | View table and view records only. |
| **Automation Maintainer** | Manage table automations without necessarily managing sharing. |

## AI Guidance

### When to Use This Feature

An AI should update table permissions when:

- A new table is created.
- A user cannot perform an expected action.
- A team should see records but not change the table design.
- Business roles require different levels of control.
- A sensitive table needs narrower access than the workspace role grants.

### How to Use It

<Steps>
  <Step title="List the user groups">
    Identify every role, team, or user group that interacts with the table.
  </Step>
  <Step title="Define actions per group">
    Decide who can view, create, edit, delete, comment, manage views, manage columns, automate, and share.
  </Step>
  <Step title="Create or edit permission sets">
    Keep names business-friendly, such as **Managers**, **Operators**, or **Read Only**.
  </Step>
  <Step title="Assign subjects">
    Add users, teams, or roles to the right permission sets.
  </Step>
  <Step title="Save and test">
    Verify with sample users.
  </Step>
</Steps>

### How to Verify

The AI should verify:

- View-only users cannot edit or delete records.
- Operators can do day-to-day work without managing columns or sharing.
- Managers can see the views and actions they need.
- Admins can recover sharing access.
- Users without access cannot open the table from the sidebar or direct links.

## Permission Design Rules

- Grant access to teams or roles where possible, not individual users.
- Avoid giving **Delete Table** or **Manage Sharing** broadly.
- Keep table design permissions separate from day-to-day record permissions.
- Re-test permissions after adding workflow buttons or automations.
