Tables are the foundation of ERPLite. A table stores one type of business record: purchase orders, sales orders, assets, work orders, SKUs, vendors, dispatches, invoices, audits, or any other operational object.

Think of a table as a business workspace, not just a spreadsheet. Tables can have rich field types, relationships, saved views, permissions, workflow actions, comments, activity history, imports, exports, automations, and reports.

## When to Use Tables

Use a table when the business needs to:

- Track a repeatable record type.
- Search, filter, import, or export operational data.
- Assign ownership to users or teams.
- Link records together, such as a vendor to purchase orders or an asset to work orders.
- Move records through business statuses.
- Trigger automations when records are created, updated, or deleted.
- Report on live operational data.

Do not create a new table for a temporary list that will never be updated, assigned, automated, or reported on. Use a saved view or report instead when the data already exists in another table.

## Core Building Blocks

| Building Block | What It Does |
|----------------|--------------|
| **Columns** | Define the fields each record stores. |
| **Records** | The individual business items users create and update. |
| **Relations** | Link one table to another so records can reference each other. |
| **Views** | Saved filters, sorts, display choices, table layouts, kanban boards, or grouped queues. |
| **Permissions** | Control who can see the table, edit records, manage columns, comment, share, or configure automations. |
| **Column permissions** | Hide or lock specific fields for selected users, teams, or roles. |
| **Workflow status** | Show where a record is in a process and what actions are available next. |
| **Automations** | Run background actions when records change or on a schedule. |

## AI Guidance

### When to Use This Feature

An AI should create or update a table when the business describes a record type that has a lifecycle, owner, team, documents, relations, approvals, reports, or recurring updates.

Examples:

- "Track raw material inventory and reorder recommendations."
- "Manage purchase orders from draft to received."
- "Create a dispatch table linked to sales orders."
- "Track preventive maintenance work orders for assets."

### How to Use It

<Steps>
  <Step title="Identify the record type">
    Name the table using the business noun users already use, such as **Purchase Orders**, **Dispatches**, or **Assets**.
  </Step>
  <Step title="Define the fields">
    Add columns for identifiers, dates, statuses, quantities, amounts, owners, teams, documents, and notes.
  </Step>
  <Step title="Add relations">
    Link the table to related business objects. For example, Purchase Orders should link to Vendors and PO Items.
  </Step>
  <Step title="Choose display fields">
    Pick the field users should recognize in relation pickers and search results, such as PO Number, Asset Name, or Customer Name.
  </Step>
  <Step title="Create daily views">
    Add saved views for the teams who will use the table, such as Open, Overdue, Assigned to Me, or Ready for Dispatch.
  </Step>
  <Step title="Configure permissions">
    Share the table with the right users, teams, or roles and grant only the actions they need.
  </Step>
</Steps>

### How to Verify

The AI should verify a table setup by checking:

- A sample record can be created without unclear or missing required fields.
- The record title/display value is readable in relation pickers.
- Search and filters return expected records.
- Related records appear on the record detail page.
- Target users can see the table and only the actions they should have.
- Imports, exports, workflows, reports, and automations use the table correctly if they are part of the process.

## Recommended Table Design Checklist

- Use clear business names for tables and columns.
- Avoid duplicate fields that mean the same thing.
- Use relation fields instead of copying names from another table.
- Use dropdown/status fields for controlled business states.
- Use derived fields for calculated totals, copied lookup values, and rollups.
- Use conditional fields when a field should only be visible, locked, or required in certain scenarios.
- Create views before inviting a large team so users start from curated queues.

<Tip>
If an AI is unsure whether to create a new table or add fields to an existing table, it should ask: "Does this item have its own lifecycle, owner, records, and reporting needs?" If yes, use a table. If not, it may be a column, relation, view, or report.
</Tip>
