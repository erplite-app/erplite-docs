The Purchase module buys things. It holds your vendors and their price lists, raises and approves purchase orders, receives the goods that arrive against them, and advises you when stock runs low.

This section is a developer reference. It documents the concepts, the permission model, and every endpoint. The rest of the ERPLite docs are written for business users and administrators; these pages assume you are writing code against the API.

<Note>
The module runs as a pilot behind an account allowlist. Your account must be enabled for `/bff-service/purchase/*` before any of these endpoints will answer. See [Authentication and roles](/purchase/auth-and-roles).
</Note>

## The mental model

Three ideas explain almost everything about how the module behaves.

**A purchase order is a promise, and its status is the whole story.** An order moves along a state machine: `draft → pending_approval → approved → partially_received → received → closed`, with `cancelled` reachable from several of those. Nothing skips a state, and no route lets you write a status directly. You call an action — submit, approve, amend, cancel, close — and the module decides what the new status is. The response always carries the order in its new state, so you never need a second read to find out what happened.

**Purchase never writes stock.** Receiving goods puts them on a shelf, but Purchase does not put them there. It calls Inventory's Receive operation across a seam, and Inventory writes the movements. Purchase holds the receipt document and the paperwork around it; Inventory holds the ledger. The two are deliberately separate systems that agree by message rather than by shared tables.

**Open supply is a position, not a query.** "What is already on order for this item at this warehouse" is an authoritative number the module maintains as orders are approved and receipts are posted. It is not derived by scanning purchase orders when you ask. This matters because that number is what the replenishment engine compares against stock — a lagging or partial answer would cause the module to order things twice.

## What the module governs, and what it does not

| Kind | Examples | Where it lives | How you change it |
|------|----------|----------------|-------------------|
| **Master data** | Vendors, the vendor-item catalog | Platform tables (`pur_vendor`, `pur_vendor_item`) | This module's endpoints, or its import pipeline |
| **Configuration** | Governance policies, reorder policies | Platform tables (`pur_policy`, `pur_reorder_policy`) | The policy endpoints — admin only |
| **Documents** | Purchase orders, goods receipts | Platform tables, changed only through the module | The document endpoints and their action routes |
| **The position** | Open supply, recommendations, the event outbox | The module's own store, not platform tables | Never directly — only as a side effect of an action |
| **Stock** | Movements and balances | **Inventory**, not here | Post a receipt; Inventory writes the movements |
